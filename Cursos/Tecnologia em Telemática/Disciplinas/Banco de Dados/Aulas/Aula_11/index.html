Mapeamento Lógico Relacional (Parte 2): Tabelas Associativas para N:M, Multivalorados, Ternários e Especialização EER

Domine a conversão formal de estruturas conceituais complexas para o Modelo Relacional em estrita conformidade com a Primeira Forma Normal (1FN): tabelas associativas com chaves compostas para relacionamentos binários e recursivos $N:M$, isolamento de coleções e atributos multivalorados em tabelas satélites, dedução analítica de chaves primárias em vínculos ternários e as 4 opções de herança do modelo EER.

Diretriz Pedagógica: Uso Exclusivo de Domínios Comuns e Cotidianos

Para garantir máxima clareza na assimilação das regras formais do Modelo Relacional e do Algoritmo de Mapeamento (Passos 5 a 8) sem dispersão cognitiva, todos os exemplos conceituais, esquemas lógicos e exercícios utilizam entidades do cotidiano (escolas, matrículas, alunos, disciplinas, clientes, salas e frotas de veículos).

Visão Geral: Por que Novas Relações São Obrigatórias?

Na Aula 10, mapeamos relacionamentos $1:1$ e $1:N$ apenas propagando uma Chave Estrangeira para uma tabela já existente. Em vínculos $N:M$ ou atributos multivalorados, tentar colocar a FK em tabelas existentes quebra a Primeira Forma Normal (1FN) (exigiria listas em células) ou a Integridade de Entidade (duplicação de PK). Por isso, os Passos 5 a 8 exigem a criação de novas relações especializadas.

Passo 5

Relacionamentos N:M

Tabela Associativa com Chave Primária Composta ($\underline{PK} = \underline{\{FK_1, FK_2\}}$) e recursivos.

Passo 6

Atributos Multivalorados

Tabela Satélite com $\underline{PK} = \underline{\{FK_E, Atributo\}}$ e exclusão em cascata (CASCADE).

Passo 7

Relacionamentos Ternários

Dedução matemática da PK a partir das cardinalidades máximas ($N:M:P$ vs. $1:N:M$).

Passo 8

Especialização EER

Opção 8A clássica de Elmasri & Navathe com chave compartilhada ($\underline{PK/FK}$) nas subclasses.

5 Passo 5: Mapeamento de Relacionamentos Binários N:M e Recursivos N:M

Para cada relacionamento binário $N:M$ (M:N) $R$ entre as entidades $S$ e $T$, cria-se uma Tabela Associativa (relação de junção) $R_{ST}$. Incluem-se como Chaves Estrangeiras ($FK$) as chaves primárias de $S$ e de $T$. A Chave Primária de $R_{ST}$ é a união obrigatória das duas FKs:

PK(R_ST) = { FK(PK_S) ∪ FK(PK_T) }

Migração de Atributos do Losango

Quaisquer atributos desenhados no losango do relacionamento (ex: data_inicio, horas_trabalhadas) tornam-se colunas simples da tabela associativa, pois descrevem a ocorrência do fato da associação.

Auto-Relacionamento Recursivo N:M

Quando a entidade relaciona-se consigo mesma em malha (ex: disciplinas acadêmicas e seus pré-requisitos), a tabela associativa recebe duas FKs apontando para a mesma chave primária com nomes semânticos claros para distinguir os papéis (cod_disc_fk e cod_pre_req_fk).

// DER: ALUNO (0,N) --- <MATRICULA (semestre, nota)> --- (1,N) DISCIPLINA
ALUNO ( matricula, nome_aluno, curso, data_ingresso )
DISCIPLINA ( cod_disc, nome_disciplina, carga_horaria )
HISTORICO_MATRICULA ( matricula_fk, cod_disc_fk, semestre_letivo, nota_final )
HISTORICO_MATRICULA.matricula_fk REFERENCES ALUNO.matricula [NOT NULL]
HISTORICO_MATRICULA.cod_disc_fk REFERENCES DISCIPLINA.cod_disc [NOT NULL]

6 Passo 6: Mapeamento de Atributos Multivalorados

Para cada atributo multivalorado $A$ da entidade $E$ (elipse dupla no DER), cria-se uma nova relação autônoma $R_A$. Propaga-se a $\underline{PK_E}$ como Chave Estrangeira ($FK$) e compõe-se a Chave Primária pela junção da $FK$ com o próprio atributo:

PK(R_A) = { FK(PK_E) ∪ Atributo_Multivalorado }
// DER: CLIENTE(id_cliente, cpf [AK], nome_completo, {telefone}, {email})
CLIENTE ( id_cliente, cpf [AK], nome_completo )
CLIENTE_TELEFONE ( id_cliente_fk, num_telefone, tipo_contato )
CLIENTE_EMAIL ( id_cliente_fk, endereco_email, tipo_email )
// Regra de Ouro: Exclusão em Cascata (ON DELETE CASCADE)
CLIENTE_TELEFONE.id_cliente_fk REFERENCES CLIENTE.id_cliente ON DELETE CASCADE
CLIENTE_EMAIL.id_cliente_fk REFERENCES CLIENTE.id_cliente ON DELETE CASCADE

7 Passo 7: Relacionamentos de Grau Superior (Ternários e n-ários)

Para relacionamentos que conectam 3 ou mais entidades, cria-se uma relação associativa com as Chaves Estrangeiras de todas as participantes. A Chave Primária depende estritamente das cardinalidades máximas:

Caso N:M:P (Todas Cardinalidades Máximas N)

PK de 3 Atributos

Todas as ocorrências combinam-se livremente. A Chave Primária precisa das três chaves estrangeiras:

PK = { FK_1, FK_2, FK_3 }

Caso 1:N:M (Uma Entidade com Cardinalidade Máxima 1)

PK de 2 Atributos Apenas

Para cada par $(E_2, E_3)$, existe no máximo uma ocorrência de $E_1$. A PK é composta apenas por $\{FK_2, FK_3\}$:

PK = { FK_2, FK_3 }; FK_1 é chave estrangeira simples

// DER Ternário 1:N:M: PROFESSOR (N) --- <ALOCA (dia_semana, horario)> --- (M) TURMA --- (1) SALA
PROFESSOR ( id_prof, nome_professor )
TURMA ( cod_turma, ano_semestre )
SALA ( num_sala, bloco )
ALOCACAO_AULA ( id_prof_fk, cod_turma_fk, num_sala_fk, dia_semana, horario )
ALOCACAO_AULA.id_prof_fk REFERENCES PROFESSOR.id_prof [NOT NULL]
ALOCACAO_AULA.cod_turma_fk REFERENCES TURMA.cod_turma [NOT NULL]
ALOCACAO_AULA.num_sala_fk REFERENCES SALA.num_sala [NOT NULL] // FK Simples (Lado 1)

8 Passo 8: Mapeamento de Especialização / Generalização (Modelo EER)

Para mapear hierarquias de herança do modelo Entidade-Relacionamento Estendido (EER), a Opção 8A de Elmasri & Navathe é a estratégia padrão recomendada:

Opção 8A: Múltiplas Relações com Chave Compartilhada (PK/FK) Cria-se uma relação para a superclasse com todos os atributos comuns. Cria-se uma relação para cada subclasse contendo seus atributos específicos mais a Chave Primária da superclasse. Nas subclasses, essa chave desempenha simultaneamente o papel de Chave Primária ($\underline{PK}$) e Chave Estrangeira ($FK$) apontando para a superclasse.
// Superclasse: VEICULO (placa, renavam [AK], marca, modelo, ano_fab, valor_aquisicao)
VEICULO ( placa, renavam [AK], marca, modelo, ano_fab, valor_aquisicao )
// Subclasses com PK/FK compartilhada (Opção 8A):
CARRO ( placa_fk, qtd_portas, tipo_cambio, volume_porta_malas_litros )
CAMINHAO ( placa_fk, num_eixos, capacidade_carga_ton, tipo_carroceria )
CARRO.placa_fk REFERENCES VEICULO.placa [ON DELETE CASCADE]
CAMINHAO.placa_fk REFERENCES VEICULO.placa [ON DELETE CASCADE]

Exercícios de Fixação e Modelagem Lógica

Exercício 1 — Passo 5: Tabela Associativa N:M e Atributos de Vínculo (ALUNO × DISCIPLINA)

Enunciado: Alunos matriculam-se em diversas disciplinas e cada disciplina possui múltiplos alunos matriculados, com atributos próprios da matrícula (semestre_letivo, nota_final, frequencia_pct).

ALUNO ( matricula, nome_aluno, curso, data_ingresso )
DISCIPLINA ( cod_disc, nome_disciplina, carga_horaria, ementa )
HISTORICO_MATRICULA ( matricula_fk, cod_disc_fk, semestre_letivo, nota_final, frequencia_pct )
HISTORICO_MATRICULA.matricula_fk REFERENCES ALUNO.matricula [NOT NULL]
HISTORICO_MATRICULA.cod_disc_fk REFERENCES DISCIPLINA.cod_disc [NOT NULL]

Justificativa Formal: Propagar a chave da disciplina para a tabela ALUNO violaria a 1FN (gerando lista/vetor de códigos em uma única célula) ou violaria a chave primária ao duplicar linhas do aluno para cada disciplina. A tabela associativa com PK composta resolve a relação elegantemente.

Exercício 2 — Passo 5 Avançado: Auto-Relacionamento Recursivo N:M (DISCIPLINA ↔ PRE_REQUISITO)

Enunciado: Uma disciplina pode exigir várias matérias pré-requisito e servir de requisito para várias outras, com atributo tipo_exigencia.

DISCIPLINA ( cod_disc, nome_disciplina, carga_horaria )
PRE_REQUISITO ( cod_disc_fk, cod_pre_requisito_fk, tipo_exigencia )
PRE_REQUISITO.cod_disc_fk REFERENCES DISCIPLINA.cod_disc
PRE_REQUISITO.cod_pre_requisito_fk REFERENCES DISCIPLINA.cod_disc

Ambas as FKs apontam para DISCIPLINA(cod_disc). Como a relação é orientada (a disciplina $D_2$ exige $D_1$, e não o contrário), o par $(D_2, D_1)$ tem semântica distinta de $(D_1, D_2)$, compondo legitimamente a Chave Primária Composta.

Exercício 3 — Passo 6: Atributos Multivalorados e Eliminação de Vetores ({telefone}, {email})

Esquemas Resultantes:

CLIENTE ( id_cliente, cpf [AK], nome_completo )
CLIENTE_TELEFONE ( id_cliente_fk, num_telefone, tipo_contato )
CLIENTE_EMAIL ( id_cliente_fk, endereco_email, tipo_email )
CLIENTE_TELEFONE.id_cliente_fk REFERENCES CLIENTE.id_cliente ON DELETE CASCADE
CLIENTE_EMAIL.id_cliente_fk REFERENCES CLIENTE.id_cliente ON DELETE CASCADE

A exclusão em cascata (ON DELETE CASCADE) é essencial porque contatos telefônicos e e-mails são atributos dependentes da existência do cliente. Se o cliente for excluído da base, seus canais de contato perdem o sentido e devem ser removidos automaticamente para evitar registros órfãos.

Exercício 4 — Passo 7: Relacionamento Ternário e Determinação da Chave Primária (1:N:M)

Caso 1:N:M (Professor + Turma utilizam no máximo 1 Sala de aula):

PROFESSOR ( id_prof, nome_professor )
TURMA ( cod_turma, ano_semestre )
SALA ( num_sala, bloco )
ALOCACAO_AULA ( id_prof_fk, cod_turma_fk, num_sala_fk, dia_semana, horario )
ALOCACAO_AULA.id_prof_fk REFERENCES PROFESSOR.id_prof [NOT NULL]
ALOCACAO_AULA.cod_turma_fk REFERENCES TURMA.cod_turma [NOT NULL]
ALOCACAO_AULA.num_sala_fk REFERENCES SALA.num_sala [NOT NULL] // FK Simples

Como para cada par (id_prof, cod_turma) existe no máximo uma sala, a Chave Primária da relação de ligação é composta apenas pelas duas FKs correspondentes aos lados N. A chave da sala entra como Chave Estrangeira simples, garantindo que o mesmo par não seja alocado simultaneamente em duas salas diferentes.

Exercício 5 — Passo 8: Especialização/Generalização EER (Opção 8A: PK/FK Compartilhada)

Esquemas Resultantes pela Opção 8A (Recomendada):

VEICULO ( placa, renavam [AK], marca, modelo, ano_fab, valor_aquisicao )
CARRO ( placa_fk, qtd_portas, tipo_cambio, volume_porta_malas_litros )
CAMINHAO ( placa_fk, num_eixos, capacidade_carga_ton, tipo_carroceria )
CARRO.placa_fk REFERENCES VEICULO.placa [ON DELETE CASCADE]
CAMINHAO.placa_fk REFERENCES VEICULO.placa [ON DELETE CASCADE]

A Opção 8A elimina 100% dos valores NULL que existiriam em uma tabela única com discriminador de tipo (Opção 8C), permitindo adicionar novos tipos de veículos no futuro sem alterar a estrutura da superclasse ou criar colunas não-aplicáveis.
