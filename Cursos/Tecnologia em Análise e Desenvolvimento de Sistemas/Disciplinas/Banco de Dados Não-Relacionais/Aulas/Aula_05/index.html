1. O Projeto Transversal: FastCommerce NoSQL

Nesta aula prática, construímos uma aplicação web real sob o padrão de Persistência Poliglota (*Polyglot Persistence*). O Redis assume o papel crítico de memória de alta velocidade ($\mu\text{s}$), mitigando o gargalo de acesso a disco que acomete os sistemas tradicionais.

Estruturas Utilizadas no Redis:
  • Strings com TTL: session:<token> para sessões ativas e cache:catalogo_produtos com expiração.
  • Hashes: cart:<session_id> para controle atômico de produtos e quantidades.
  • Listas (Queue): fila:pedidos para o desacoplamento do checkout assíncrono.
A Conexão com o MongoDB (Aula 06):
  • Finitude da Memória: O Redis retém apenas dados transitórios de alta frequência.
  • Camada Permanente: O worker de pedidos gravará os documentos definitivos no MongoDB na próxima aula.
  • Catálogo Flexível: O catálogo deixará de ser um mock para se tornar uma coleção rica em documentos BSON.
Pilar 1

Cache-Aside com TTL

A API consulta o Redis primeiro. Se houver miss, busca no disco, grava com SETEX e retorna. Latência cai de 120ms para 0.4ms.

Pilar 2

Sessão Distribuída

Tokens de sessão centralizados no Redis com expiração deslizante (EXPIRE), permitindo escala horizontal transparente.

Pilar 3

Carrinho em Hashes

Operações com HINCRBY garantem atomicidade nativa e eliminam condições de corrida sem lock síncrono.

Pilar 4

Fila Assíncrona

Checkout com LPUSH e processamento em background com BRPOP bloqueante sem sobrecarga de CPU.

    pedido = {"id_pedido": f"PED-{int(time.time())}", "itens": itens, "status": "ENFILEIRADO"}

3 Etapa 3: Gestão de Sessões em Memória com Expiração Deslizante (SETEX / EXPIRE)

Necessidade: Sessões em memória de um único processo impedem o balanceamento de carga e sessões em disco são lentas. No Redis, usamos chaves session:<uuid> com TTL de 1800 segundos renovado a cada clique (Sliding Expiration). 

def obter_ou_criar_sessao(req):
    session_id = req.cookies.get("fastcommerce_session") or str(uuid.uuid4())
    chave = f"session:{session_id}"
    if not r.exists(chave):
        # SETEX atômico: grava e define TTL de 30min sem risco de chaves órfãs na RAM
        r.setex(chave, 1800, json.dumps({"usuario": "Estudante ADS", "perfil": "Cliente VIP"}))
    else:
        # Usuário navegando: renova o TTL para mais 30min
        r.expire(chave, 1800)
    return session_id
# Teste de verificação no redis-cli: $ redis-cli TTL "session:8a31c510-fd11-4f18-b0a3-677a28e9cf94"
(integer) 1795 (tempo decrescendo segundo a segundo)
4 Etapa 4: Catálogo com Padrão Cache-Aside e TTL (Speedup > 250x)

Necessidade: Proteger o banco principal de avalanche de requisições de leitura, mantendo consistência eventual através de TTL de 45 segundos e rota de invalidação manual (DEL). 

@app.route("/api/produtos", methods=["GET"])
def get_produtos_cache_aside():
    inicio = time.time()
    chave = "cache:catalogo_produtos"
    if r.exists(chave): # CACHE HIT
        produtos = json.loads(r.get(chave))
        origem = "CACHE_HIT (RAM Redis)"
    else:               # CACHE MISS
        time.sleep(0.12)
        produtos = CATALOGO
        r.setex(chave, 45, json.dumps(produtos)) # Armazena com TTL de 45s
        origem = "CACHE_MISS (Disco/SGBD)"
    latencia = round((time.time() - inicio) * 1000, 2)
    return jsonify({"origem": origem, "latencia_ms": latencia, "ttl": r.ttl(chave)})
# Teste de comparação de latência: 1ª Requisição (MISS): { "origem": "CACHE_MISS", "latencia_ms": 120.52, "ttl": 45 }
2ª Requisição (HIT): { "origem": "CACHE_HIT", "latencia_ms": 0.42, "ttl": 44 }
>> Aceleração comprovada: 286x mais rápido!
5 Etapa 5: Carrinho de Compras Atômico em Hashes (HINCRBY / HDEL)

Necessidade: Evitar condições de corrida (Race Conditions) quando o usuário clica rápido ou abre várias abas. Hashes permitem alterar campos individuais de forma atômica na CPU do Redis sem ler ou serializar o objeto inteiro. 

# Adiciona item ao carrinho atômica e nativamente no Redis
r.hincrby(f"cart:{session_id}", produto_id, quantidade)
r.expire(f"cart:{session_id}", 3600) # Carrinho abandonado expira após 1 hora

# Leitura do carrinho completo em O(N) itens
itens = r.hgetall(f"cart:{session_id}") # Retorna {'prod_1': '2', 'prod_3': '1'}
# Teste de inspeção no redis-cli: $ redis-cli HGETALL "cart:usr_8a31c510"
1) "prod_1"   2) "2"
3) "prod_3"   4) "1"
6 Etapa 6: Checkout Assíncrono com Fila (LPUSH)

Necessidade: Validação bancária e emissão de NFe levam 5+ segundos. Em vez de travar o cliente HTTP, enfileiramos o pedido em 0.3 ms e liberamos o navegador. 

# Enfileira na lista FIFO do Redis e deleta o carrinho
r.lpush("fila:pedidos", json.dumps(pedido))
r.delete(f"cart:{session_id}")
return jsonify({"status": "ENFILEIRADO", "posicao": r.llen("fila:pedidos")})
7 Etapa 7: Worker com Bloqueio Inteligente (BRPOP)

Necessidade: Consumir pedidos sem fritar a CPU em um loop com sleep. BRPOP bloqueia o processo com 0% de CPU até que um item chegue. 

while True:
    # Bloqueia por até 5s aguardando itens (0% consumo de CPU)
    item = r.brpop("fila:pedidos", timeout=5)
    if item:
        _, pedido_json = item
        processar_pedido(json.loads(pedido_json))

Questão 1: Padrão Cache-Aside e Invalidação

Explique por que a estratégia recomendada ao alterar o preço de um produto em um banco de dados é executar DEL cache:produto em vez de SET cache:produto <novo_preco>.

Questão 2: Atomicidade e Hashes no E-commerce

Durante uma promoção de Black Friday com milhares de compras simultâneas, por que o comando HINCRBY cart:usr_1 prod_1 1 é muito mais seguro e performático do que desserializar um JSON, alterar no Python e salvar de volta com SET?

Questão 3: Políticas de Expiração (TTL)

Diferencie Absolute Expiration (expiração rígida) de Sliding Expiration (expiração deslizante), citando em qual situação cada uma foi aplicada no FastCommerce (catálogo vs. sessão).

Questão 4: Filas Bloqueantes (BRPOP vs. RPOP)

Por que a implementação de workers com BRPOP chave timeout é superior à implementação com loop infinito usando RPOP intercalado com time.sleep(1)?
