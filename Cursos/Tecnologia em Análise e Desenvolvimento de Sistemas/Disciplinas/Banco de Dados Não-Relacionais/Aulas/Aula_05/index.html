1. O Projeto Transversal: FastCommerce NoSQL

Nesta aula prática, construímos uma aplicação web real sob o padrão de Persistência Poliglota (*Polyglot Persistence*). O Redis assume o papel crítico de memória de alta velocidade ($\mu\text{s}$), mitigando o gargalo de acesso a disco que acomete os sistemas tradicionais.

Estruturas Utilizadas no Redis:
  • Strings com TTL: session:<token> para sessões ativas e cache:catalogo_produtos com expiração.
  • Hashes: cart:<session_id> para controle atômico de produtos e quantidades.
  • Listas (Queue): fila:pedidos para o desacoplamento do checkout assíncrono.
A Conexão com o MongoDB (Aula 06):
  • Finitude da Memória: O Redis retém apenas dados transitórios de alta frequência.
  • Camada Permanente: O worker de pedidos gravará os documentos definitivos no MongoDB na próxima aula.
  • Catálogo Flexível: O catálogo deixará de ser um mock para se tornar uma coleção rica em documentos BSON.
Pilar 1

Cache-Aside com TTL

A API consulta o Redis primeiro. Se houver miss, busca no disco, grava com SETEX e retorna. Latência cai de 120ms para 0.4ms.

Pilar 2

Sessão Distribuída

Tokens de sessão centralizados no Redis com expiração deslizante (EXPIRE), permitindo escala horizontal transparente.

Pilar 3

Carrinho em Hashes

Operações com HINCRBY garantem atomicidade nativa e eliminam condições de corrida sem lock síncrono.

Pilar 4

Fila Assíncrona

Checkout com LPUSH e processamento em background com BRPOP bloqueante sem sobrecarga de CPU.

2. Código Essencial: Produtor (API) e Consumidor (Worker)

Veja como o desacoplamento assíncrono é implementado de forma limpa com as estruturas nativas do Redis: 

# PRODUTOR: A rota de checkout apenas enfileira o pedido e libera o cliente
@app.route("/api/checkout", methods=["POST"])
def checkout():
    itens = r.hgetall(f"cart:{session_id}")
    pedido = {"id_pedido": f"PED-{int(time.time())}", "itens": itens, "status": "ENFILEIRADO"}
    
    # LPUSH insere na ponta esquerda da lista em microssegundos (< 1 ms)
    posicao = r.lpush("fila:pedidos", json.dumps(pedido))
    r.delete(f"cart:{session_id}")
    return jsonify({"pedido": pedido, "posicao_fila": posicao})

# CONSUMIDOR: O worker escuta com BRPOP (bloqueio de baixo consumo de CPU)
def processar_pedidos():

Exercícios de Fixação Conceitual

Questão 1: Padrão Cache-Aside e Invalidação

Explique por que a estratégia recomendada ao alterar o preço de um produto em um banco de dados é executar DEL cache:produto em vez de SET cache:produto <novo_preco>.

Questão 2: Atomicidade e Hashes no E-commerce

Durante uma promoção de Black Friday com milhares de compras simultâneas, por que o comando HINCRBY cart:usr_1 prod_1 1 é muito mais seguro e performático do que desserializar um JSON, alterar no Python e salvar de volta com SET?

Questão 3: Políticas de Expiração (TTL)

Diferencie Absolute Expiration (expiração rígida) de Sliding Expiration (expiração deslizante), citando em qual situação cada uma foi aplicada no FastCommerce (catálogo vs. sessão).

Questão 4: Filas Bloqueantes (BRPOP vs. RPOP)

Por que a implementação de workers com BRPOP chave timeout é superior à implementação com loop infinito usando RPOP intercalado com time.sleep(1)?

Questão 5: Persistência Poliglota com MongoDB

Discuta as razões técnicas pelas quais uma loja virtual moderna utiliza o Redis para carrinhos e sessões em trânsito, mas transfere os pedidos finalizados para o MongoDB na camada de persistência definitiva.
